## 主要不足和卡点

### 1. 正式证据准入对个别 Query 不够稳健

Q-0003 在 S1–S6 后触发武器装备 Recall。首次和重试均出现 3 条候选证据正式接纳 0 条，最终被停止策略拦截。该失败可稳定复现，说明不是瞬时模型错误，而是检索、材料化、来源域覆盖或证据 ID 追溯链的结构性缺口。

建议：在进入 Recall 前显示缺失的证据类型和来源域；为装备型号/参数类 Recall 增加权威来源定向检索；允许在不降低门槛的前提下扩展检索批次；对无效证据 ID 在 S4–S6 生成时提前拦截。

### 2. 墙钟预算不能覆盖多轮中循环长尾

Q-0009 首次已完成两轮 S1–S6，却在交付前触发 `wall-clock budget expired`。固定预算对复杂 Query 不够自适应。

建议：按已完成阶段动态续预算；Reporter/审计使用独立交付预算；预算临界时优先保存可恢复检查点，不在 S6 完成后直接判整次失败。

### 3. 断点恢复粒度偏粗

Q-0009 重试复用了 Packet Admission 和基线结果，但仍重新执行收敛与制胜机理，而不是从 S6 后直接进入审计/Reporter，造成重复调用和额外成本。

建议：为基线、收敛、S1–S6、审计、Reporter 分别保存阶段完成标志与输入哈希；配置和输入未变化时，从最近完整阶段恢复。

### 4. 真实审计模型稳定性不足

19 个完成任务中，13 个触发 `audit_model_fallback`（68.4%）；最终仅 5 个为 `approved`，14 个为 `limited`。所有 19 份报告的报告质量门均显示通过，但多数审计结论仍为 limited，两个门控口径存在展示上的割裂。

建议：增加审计专用超时和有限重试；缩短审计输入；在前端同时展示“报告质量门”和“五判据审计状态”；limited 报告不得与 approved 使用相同完成标识。

### 5. 阶段可观测性仍不够细

任务经常数分钟停留在上一个 `winning_subagent_completed` 或笼统 `tool_call`，但后台实际正在执行下一个高推理模型调用。仅看百分比或最后完成事件容易误判卡死。

建议前端显示：当前阶段/Agent、模型调用已运行秒数、当前中循环、Recall/重试次数、是否等待模型并发、Reporter/审计状态、墙钟预算剩余量。

### 6. 成本统计缺失

`round_summary.json` 中 `usage` 为空。虽然可以统计 230 次调用和 8.78 小时累计模型执行时间，但无法准确汇总输入/输出 Token 与费用。

建议：Codex provider 持久化每次调用的 token usage、模型、重试、缓存命中和估算费用，并按 Query、Agent、阶段汇总。
