# 01_项目已进入可演示可评测可审计阶段

本次汇报的核心结论是，项目已经不是把多个 Agent 拼在一起的功能原型，而是形成了从问题定义到审计交付的研究操作系统。AI Query 负责把研究入口标准化，质量集群和动态蜂群在同一条制胜机理链上提供不同的执行强度，专家评审和报告模板保证结果可以治理、追溯和交付。后面我们会先看入口如何建立，再说明两种策略为什么能服务不同复杂度的任务。

---

# 02_AI_Query双模式

这一页先澄清一个关键认识：需求 Query 不是让模型一次性吐几个标题，而是一个独立、异步运行的选题发现服务。左侧的“围绕母题发散”，由用户给出课题边界，例如复杂电磁环境下的精确打击需求，再补充需求牵引、技术驱动等约束，系统从需求、技术、体系、颠覆和规模建设等不同角度，拆出互不重复的研究入口。右侧的“自动态势发散”则不要求用户先有题目：系统守住无人、低空、远程火力和精确打击等领域边界，Agent 从公开态势与技术信号中自己挑出值得研究的矛盾和机会。最大的区别不是模型能力，而是问题边界由谁定义：前者是用户，后者是系统。两种模式进入的是同一条受治理链路：联网校验、20 个覆盖槽位的结构化生成、质量去重与来源校验、草稿审核发布，再进入 Deep Research。联网来源只帮助形成选题线索，不能替代正式报告中的证据。

---

# 03_Query前端工作台

这不是一个会卡住页面的生成按钮。前端调用接口后只创建任务，独立 Query Worker 会异步领取并执行；页面会明确显示排队、联网校验、Query 生成、保存中和完成或失败，用户离开也不影响任务，失败可以重试。运行时先做轻量联网校验，读取 3 到 5 个公开检索线索，最多保留 8 个实际访问的 HTTPS 来源；之后按 20 个覆盖槽位生成 4 到 20 条 Query，并做单条质量、去重和来源校验，整批通过才原子写入草稿库。每条草稿不只是短标题，还带有覆盖视角、研究边界、形成理由和来源线索；人工审核发布后才带入 Deep Research。右侧是项目真实工作台，现场可以直接演示这一闭环。

---

# 04_共享S1S6主链

接下来不急着讲技术名词，先讲它们在解决什么问题。无论选质量集群还是动态蜂群，大家都在走同一条研究路：先看清问题，再想出方向，拿证据核验，最后形成可交付结论。差别只在带队方式：质量集群像固定、成熟的专家组快速会诊；动态蜂群像遇到新疑点才临时请来的专项顾问。两种方式共同的目标，是不让没有依据、经不起推敲的方案走到最后。

---

# 05_质量集群策略

质量集群就像一次有章法的专家会诊。先提出几个可能方向，再让检索、红队、可行性和验证等固定专家分工补证据、挑毛病；每一轮都检查有没有新增价值，没有就不再加人。这样，系统不会因为人越来越多而意见越来越乱，出了问题也能从检查点恢复。它的价值是用可控的时间和预算，把复杂问题先收敛成几条值得继续研究的稳定方向。

---

# 06_动态蜂群策略

动态蜂群适合研究做到一半发现真正难点的时候。比如证据不够、因果说不通、装备不具体、对手会怎样反应还没想清，或者没有验证办法，系统才临时请最合适的专项顾问加入。每位顾问只负责补一个明确短板，完成就离场；每条新意见都要写进同一本候选账，不能悄悄把旧结论改掉。它花的时间更多，但换来的是把复杂课题的漏项逐一补齐，让结论能经得住追问。

---

# 07_Kimi动态孵化思想

这里提到 Kimi K3，借鉴的是一种很朴素的组织思路，而不是直接复刻外部产品：问题出现才请对的人，而不是先把所有人都拉进来。新来的角色只办一件清楚的事，所有意见放到同一本账上比较，不把多个相近方案硬拼成一个看似全面的答案。谁可以加入由统一调度来决定，任务结束就回收。项目把这种思路做成了自己的 winning_swarm_dynamic_v2，确保动态增援带来的是质量提升，而不是复杂度膨胀。

---

# 08_真实运行对比

怎么选很简单：如果现在最需要的是快速把方向摸清，就选质量集群；如果要拿出能对外承担的正式结论，就选动态蜂群。同一 Query 的真实运行中，质量集群大约十分钟完成快速初筛；动态蜂群大约三十一分钟，最终达到了百分之百来源绑定、L1 到 L3 通过和 approved。多出来的时间不是空耗，而是用在补漏、独立复核和定向修复上。也就是说，前者帮我们快，后者帮我们稳。

---

# 09_质量门与独立评审

质量提升的最后一道保险，是不让看起来很完整的方案直接变成正式结论。独立专家不参加原始讨论，只看候选和有效证据，先问三件事：说得通吗，落得下吗，站得住吗。达标的进入正式收敛，缺关键一块的只做定向补齐，经不起复核的就阻断发布并留下原因。我们已经把“标题看起来很多、内容却重复”和“装备不够具体”从提醒升级为硬门，所以质量不是最后一句承诺，而是每一步都能拦住不合格方案。

---

# 10_前端成果

这两张是真实工作台页面，分别回答两个项目方最关心的问题：研究是怎样推进的，以及研究得到了什么。左侧可以看到任务执行过程中的实时交互与事件，右侧是形成后的能力画像与结构化卡片。现场建议从同一任务入口依次下钻过程、证据组织和能力结果，让项目方看到的不是一个黑盒报告，而是可跟随、可检查的研究过程。

---

# 11_结果可视化

过程可见之后，再来看结论如何被带到前端。这里展示的是项目真实的制胜结果视图：制胜机理、结果总览与任务门控状态集中在一个页面，便于项目方先理解形成的装备方向，再根据需要回看对应的 S 节点和过程信息。它的价值不是把复杂研究压缩成一张漂亮卡片，而是给评审和沟通提供一个从结论回到机制、从机制回到过程的可视化入口。

---

# 12_S1S6与证据中心

接下来把镜头从结果拉回到研究的中段。左图是同一真实任务的 S1–S6 Agent 页面：研究路线、输入包、证据索引、共享受控资源以及六个专用 Agent 的结果节点都可查看。右图是同一任务的证据中心，每条证据不仅有来源，还保留它支撑的主张、创建它的 Agent、证据标识、质量评估和来源位置。因此项目方可以从机制推演一路下钻到具体证据，而不是只接受一条汇总结论。

---

# 13_报告评审闭环

研究进入交付阶段后，报告也不再脱离任务单独存在。这个真实报告评审页面左侧保留已完成任务和状态，右侧直接呈现当前任务的研究报告；需要时还可以回到交互过程、证据中心、S1–S6 Agent 和能力画像。这样汇报和评审面对的是一份可阅读的报告，同时保留返回研究过程与证据的入口，形成真正不断线的交付闭环。

---

# 14_多模式多模板

除了两条蜂群策略，系统还将运行模式和报告表达做成可配置能力。任务可以通过 CLI 或 API 选择兼容回滚、普通协同、质量集群或动态蜂群，配置会随任务和运行快照保存，支持复现和审计。交付端可以按项目方需要选择项目论证五章模板或三层九项模板；模板改变的是阅读与决策视角，不改变事实、证据和审计边界。

---

# 15_下一阶段

下一阶段坚持一个原则：质量硬门不降级，运行效率可持续优化。证据侧将增强主张与来源的直接对应、正文可核查呈现、时效校验、冲突证据处理和专家复核；效率侧将提前按装备族和验收变量去重，减少同族重复候选，并优化动态 Agent 编排。我们会保留质量集群用于快速探索、动态蜂群用于正式收敛的双策略，并以来源绑定、交付硬门、运行时长和前端闭环演示作为下一轮验收的共同指标。
