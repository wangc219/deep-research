# 需求挖掘模块共识与待讨论问题

日期：2026-06-08

本文整理“需求挖掘模块”的阶段共识与后续需要逐项讨论的问题。本文只沉淀对后续实现有直接影响的设计结论和待决问题，不记录讨论过程中的临时角色、临时表述或已被排除的方案。本文是讨论稿，不表示最终需求、最终架构或已确认验收标准。

## 1. 模块定位共识

需求挖掘模块面向装备研发早期论证、预研选题和技术路线规划。它不直接生成成熟装备方案，而是从公开资料和授权资料中发现可讨论的需求假设、能力缺口和技术创新方向，并形成可供用户或专家判断的调查报告。

模块主要发现对象包括：

- 装备能力需求。
- 技术需求。
- 任务场景需求。
- 能力缺口。
- 技术创新方向。

模块主要输出包括：

- 需求清单。
- 能力缺口清单。
- 技术路线线索。
- 候选课题。
- 单个需求的详细调查报告。

模块应具备的核心能力包括：

- 自动搜集指定来源资料。
- 自动形成研究计划。
- 自动交叉验证资料。
- 直接抽取显式需求。
- 基于多源资料组合推断隐含需求。
- 提出新需求假设，并给出证据、论证链和不确定性。

系统输出的需求不直接等同于最终结论。讨论通过的需求交给用户，由用户决定是否进入后续方向判断、专家评审、预研选题或技术路线设计。

## 2. 产品形态共识

当前至少存在两种产品形态。

第一种是用户主动触发的专题调研。用户输入一个方向、问题、装备场景、技术线索或初步设想后，系统围绕该主题制定研究计划，检索和阅读资料，形成候选需求和调查报告。

第二种是静默扫描推送。系统持续监控指定来源，发现新的场景变化、对抗环境变化、装备动态、技术瓶颈或能力缺口线索后，主动推送给用户。

两种形态可以共享底层资料处理、证据卡片、候选需求生成、debate 和报告生成能力，但一期可以先聚焦一种形态。当前更适合优先讨论“用户主动触发专题调研”，因为它的输入、边界和验收更容易定义。

## 3. 与现有知识图谱主线的关系

需求挖掘模块不应与当前“原理-技术-能力-应用”路线发现主线混为一谈。需求发现不需要预设固定推导链条，也不应强制把所有发现结果组织成固定四层路线。

当前共识是：

- 需求挖掘模块可以在详细调研阶段调用知识图谱，用于补充例证、查找关联、验证技术路线或发现相关场景。
- 需求挖掘出的候选需求不直接写入事实图谱。
- 候选需求需要经过人为验证后，才能决定是否进入后续知识沉淀、图谱扩展或项目流程。
- 图谱在该模块中更偏辅助证据检索和关联分析，而不是候选需求的默认承载层。

## 4. 需求对象建模共识

需求应首先被定义为问题、缺口或新能力空间的陈述，而不是方案、装备或技术本身。

当前工作定义为：

> 需求是指在特定任务场景、威胁/对抗环境、约束条件或技术可行性变化下，现有能力状态与目标能力状态之间出现差距，或出现值得探索的新能力空间，由此形成的、可由证据支撑的能力改进或应用形态诉求。

需求不一定只由痛点引出。需求触发因素至少包括：

- 痛点驱动：现有问题、瓶颈、失效、不适配或不满意现象暴露出能力缺口。
- 场景驱动：新任务、新环境、新对抗条件或新使用方式要求新的能力组合。
- 技术牵引：新技术、新材料、新算法、新制造方式或新组织方式使过去不可行的能力状态变得可探索。
- 残余缺口：已有方案已经存在，但仍未充分覆盖某些场景、约束、性能或保障问题。

因此，需求挖掘模块不应只执行“痛点 -> 需求”的单一路径，而应采用更通用的链路：

```text
触发因素
-> 场景/技术/对抗/约束变化
-> 能力状态变化分析
-> 缺口或机会空间识别
-> 需求陈述
-> 证据与不确定性
```

其中，能力缺口也不只表示现有短板，还应覆盖：

- 未满足缺口：现有能力不够。
- 残余缺口：已有方案没有完全解决。
- 新场景缺口：场景变化后原有能力不适配。
- 能力跃迁空间：新技术使过去不可行的能力状态变得可探索。
- 新应用形态空间：新技术或新场景组合出原先没有的使用方式。

需求本身应包含明确的前因后果，而不是只给一个方向名或技术名。一个候选需求至少应尝试说明：

- 任务场景：该需求出现在哪类任务、装备应用或作战/保障场景中。
- 威胁或对抗环境：是什么变化、压力或外部条件触发了需求。
- 能力缺口：现有能力、装备、方法或技术路线哪里不足。
- 约束条件：环境、资源、工程、时间、成本、可靠性、适配性等限制。
- 证据来源：该判断来自哪些资料、哪些证据片段、哪些交叉验证结果。
- 论证链：系统如何从证据推导出该需求，哪些是直接证据，哪些是模型推断。
- 不确定性：有哪些反证、疑点、缺失资料或待验证问题。

需求需要区分“显式需求”和“推断需求”。

- 显式需求：资料中直接表达了需求、缺口、问题、短板或需要提升的能力。
- 推断需求：资料没有直接说出需求，但多个证据共同指向某个未满足问题、残余缺口或潜在能力需求。

允许系统提出资料中未直接写出的需求假设，但必须保留证据、推断依据、反证和不确定性。可以由一个 agent 提出假设，再由其他 agent debate、补充证据或质疑，最终形成详细方案。

资料中的方案、装备形态、技术路线或作战方式设想不应作为需求挖掘主链路的最终结论。它们更适合作为需求分析报告中的附录或相关设想，用于说明已有资料中已经出现了哪些解决方向、这些方向试图回应什么需求、是否仍存在未解决缺口。

需求标题和需求陈述不设固定句式。系统应被引导表达问题、缺口、新能力空间或应用形态诉求，而不是套用固定模板。标题可以短，陈述负责补全场景、触发因素、能力状态、证据依据和不确定性。审核时关注标题和陈述是否能让用户判断该需求在什么场景下成立、要解决什么缺口或探索什么新能力空间、为什么不是单纯技术热点或方案口号。

技术牵引型需求也不设固定表达。系统应遵循方法论而不是句式模板：先说明技术可行性变化带来了什么新的能力可能，再说明该能力可能落到什么任务场景或应用形态，最后说明为什么形成值得讨论的需求假设。若停留在技术可行性变化，则只是技术热点；若说明了能力变化但缺少场景，则只是新能力观察；只有落到任务场景中的能力诉求，才可能成为候选需求。

需求粒度暂不强行限定。无论是体系级、装备级、分系统级、部件级、材料/工艺级，只要确实揭示了未满足问题或残余缺口，都可能是有效候选需求。已有解决方案但没有完全解决问题时，残余问题也应视为能力缺口候选。

## 5. 数据来源共识

一期信源应人为指定，模型负责在指定范围内判断资料是否可用、是否可信、是否值得进一步读取。模型不应自行无限扩展到不可控平台。

甲方设计案中“市场需求”部分可作为初始讨论范围，重点包括：

- 军事理论。
- 作战运用。
- 制胜机理。
- 同行动态。
- 装备现状。
- 制胜机制的历史演变。
- 作战样式的历史演变。
- 装备图像的历史演变。
- 新的装备能力需求。

可能的数据来源类别包括：

- 军事网站。
- 军事期刊。
- 智库报告。
- 防务媒体。
- 军事理论与作战概念材料。
- 演训报道与战例分析。
- 装备发展动态。
- 同行或对手动态。
- 专利、标准、项目公告、技术白皮书。
- 公众号、媒体文章和二手分析材料。

国外公开资料应纳入需求分析，但具体来源、可信度分层和使用边界需要进一步确认。

“技术侧”更准确地说，应理解为解决路径、供给侧资料或技术支撑资料，而不是按照学科把军事需求切开。需求挖掘主线应围绕军事任务、装备体系、作战场景、对抗环境和能力缺口；技术资料主要用于判断已有方案解决到什么程度、还剩什么缺口、可能有哪些可讨论技术路线。

资料需要保留来源、发布时间、机构立场、是否二手转述等元数据，供模型初筛和人工审核判断。

一期采用甲方设计案中的军事需求数据源作为白名单基础。模型只在白名单内采集和判断；如果发现白名单外高价值来源，只能提出“建议新增信源”，不能自动纳入正式采集。

信源按其能否支撑需求判断分为四级：

- A 级强证据信源：可用于支撑正式报告中的关键判断。包括官方军事理论、政策、作战概念、装备发展相关公开材料，军事科学院、国防高校、专业学会等机构材料，经过同行评审或严肃编辑流程的军事、战略、国际安全、装备类期刊，以及 RAND、IISS、CSIS 等有完整报告结构和明确机构背景的智库报告。
- B 级专业参考信源：用于发现线索、补充动态和交叉验证，单独支撑正式需求时需要谨慎。包括简氏、防务新闻、Defense One 等防务媒体，以及远望智库、空天防务观察、蓝军开源情报等专业观察类来源。
- C 级线索信源：只用于发现 `raw_signal` 或 `researchable_signal`，不能单独支撑正式需求报告。包括公众号文章、二手转述、媒体转载、无完整出处但有启发性的观点材料。
- D 级排除信源：默认不采集或不进入需求分析流程。包括无来源、无作者、无出处的拼接内容，明显营销、标题党、SEO、搬运号，论坛传闻、社交媒体碎片，非公开、疑似泄露、敏感来源，以及无法审计来源链的材料。

信源分级影响状态流：

- 只有 C 级线索时，最多进入 `raw_signal` 或 `researchable_signal`。
- 有 B 级支撑时，可以进入 `candidate_demand`，但通常需要补证。
- 有 A 级或多源 B 级交叉支撑时，可以进入审核 agent 的正式审核。
- D 级不进入流程，只记录排除原因。

正式需求报告不能只由 C 级线索支撑。

文档级审核采用轻量门禁，不在粗筛阶段填写完整档案。粗筛阶段只保留最小必填字段：

- source_id。
- source_tier。
- title。
- publish_time。
- source_name。
- source_type。
- collection_decision。
- skip_reason。

`collection_decision` 采用四类：

- `use_as_evidence`：可以作为需求判断证据。
- `use_as_background`：只作为背景趋势。
- `use_as_signal_only`：只作为线索，不能支撑正式结论。
- `skip`：不使用。

按需补充字段只在资料进入 `candidate_demand` 或正式报告时填写：

- author_or_org。
- is_repost。
- original_source。
- institutional_stance。
- topic_relevance。

因此，文档级审核流程为：

```text
粗筛：只填最小字段
进入候选需求：补作者/转载/立场/证据角色等字段
进入正式报告：形成完整来源审计
```

摘要与全文阅读采用“广泛采集、重要性分流、任务触发精读”的策略。一期不应全量阅读全文，也不应只依赖摘要形成需求判断。系统先在指定信源中广泛采集资料，再根据标题、来源等级、发布时间、栏目/标签、摘要或导语、关键词命中、主题聚类和相关度进行分流，由不同 agent 阅读不同类型文章。

摘要字段保持最小化：

- `summary_text`：摘要或压缩概述内容。
- `summary_source`：摘要来源和正文可见性。

`summary_source` 可先采用：

- `structured_abstract`：页面、数据库或期刊页有明确摘要字段。
- `lead_summary`：正文导语或开头段落可作为摘要。
- `model_generated`：模型基于可见正文片段生成摘要。
- `body_unavailable`：正文不可见，仅有标题、残缺信息或无法稳定访问正文。

`model_generated` 只能作为阅读辅助，不能作为正式证据。`body_unavailable` 不能直接支撑候选需求或正式报告，只能作为弱线索或跳过。全文阅读触发原因不作为摘要元数据扩张，记录在阅读任务、补证动作或 trace 中。

是否全文阅读由文章重要性和任务需要触发，不由读取难度决定。读取难度只影响调度、分段、是否需要工具辅助或人工介入，不作为“不读”的主要理由。

全文阅读触发信号包括：

- A 级来源且标题或主题高度相关。
- 标题、摘要、导语或关键词命中需求、缺口、痛点、新能力空间、残余缺口等信号。
- 文章可能补齐 `CandidateDemand` 的任务场景、能力缺口、证据或不确定性字段。
- 文章可能支撑或反驳关键 claim。
- 文章可能帮助判断某个过泛需求是否需要拆分。
- 文章即将作为正式报告中的关键证据来源。

关键词检测可作为低成本早期门禁，但不能作为唯一标准。可先关注以下词组：

- 需求类：需求、能力需求、亟需、需要、迫切、牵引。
- 缺口类：短板、不足、瓶颈、难以、受限、制约、挑战。
- 场景类：作战运用、任务场景、演训、对抗、复杂环境。
- 变化类：演变、趋势、新威胁、新样式、新形态。
- 装备类：装备现状、体系建设、能力生成、保障、部署。
- 方案残余类：仍然、尚未、难以满足、有待提升、局限。

阅读层级采用递进式策略：

```text
第 0 层：标题 + 来源 + 时间 + 栏目/标签
第 1 层：摘要、导语、结论、小标题
第 2 层：与 claim 或候选需求相关的正文片段
第 3 层：全文精读
```

分层阅读用于判断文章是否值得全文阅读，也用于控制阅读成本。凡是进入 `candidate_demand` 或 `demand_report` 的关键判断，必须回到原文证据片段，不能只依赖标题、摘要或模型生成摘要。

判断已有方案是否充分解决问题时，不应只读当前文章全文，而应触发重检索任务。重检索需要提出明确验证问题，例如：

- 现有方案覆盖哪些场景？
- 它解决了哪些能力缺口？
- 哪些性能、约束、体系集成或证据问题仍未解决？
- 是否存在反例、失败案例、限制条件或不同来源的质疑？

全文阅读停止条件按候选需求、字段、claim、主题簇或验证任务定义，而不是按“连续阅读若干篇文章”定义。可停止的情况包括：

- 当前候选需求关键字段已补齐。
- 当前关键 claim 已有足够非 C 级证据支撑。
- 反证和限制条件已记录。
- 当前验证问题已被回答。
- 剩余待读资料只会重复已覆盖观点。
- 到达本轮调研预算、用户设定深度或安全边界。

agent 在阅读过程中可以主动发现、登记、扩检和拆分需求。若发现潜在需求、能力缺口、新场景、新技术牵引空间或残余缺口，可触发：

```text
initial_demand_registration
-> expansion_query_plan
-> 扩大范围检索
-> 补充文档采集
-> 更新 CandidateDemand 或 researchable_signal
```

初步登记应进入共享 `demand_registry` 或 `signal_registry`，供所有 agent 查重、合并和避免重复选题。登记字段至少包括：

- registry_id。
- 标题或暂定名称。
- 原始线索。
- 触发类型。
- 核心场景或关键词。
- 当前状态。
- 发现 agent。
- 发现来源。
- 相似候选需求。

扩检必须围绕已登记线索或候选需求，并记录触发原因、检索问题和来源范围。扩检结果不能直接进入报告，仍需经过证据卡和审核 agent。

过泛需求可以由 agent 拆分。拆分依据包括任务场景、能力环节、威胁/环境、装备对象、约束条件和技术瓶颈。拆分后的子需求分别验证，父级泛需求作为主题簇或父级问题保留，不直接作为正式候选需求。

## 6. 挖掘方法共识

模块应同时具备直接抽取和组合推断能力。

直接抽取用于识别文本中明确表达的需求、问题、短板、能力不足、环境约束、对抗压力或技术瓶颈。

组合推断用于识别资料中没有直接表达的隐含痛点。例如，多篇资料分别描述了任务变化、对抗压力、装备局限、已有方案不足和新技术迹象，系统可以综合推断出候选需求。

一个可能的 agent 流程如下：

1. 粗筛 agent：扫描指定信源，识别潜在有价值资料。
2. 摘要与聚类 agent：形成资料摘要，将相似信息聚成主题簇。
3. 定性分析 agent：判断主题簇属于需求线索、背景趋势、技术热点、装备动态、反证材料还是低价值信息。
4. 深入调研 agent：对高潜力主题检索更多资料，必要时读取原文。
5. 需求分析 agent：判断是否存在显式需求、推断需求、能力缺口或残余缺口。
6. 质疑 agent：判断证据是否不足、是否只是普通趋势、是否只是技术热点、是否已有方案充分解决。
7. 审核 agent：根据评审量表进行结论判断，决定通过、补证、降级或淘汰，并生成审核报告用于溯源。
8. 报告 agent：生成最终调查报告和来源审计信息。

需求触发模板不宜一开始完全靠预设脑测。可以在初期只保留少量提示词或启发式线索，例如“新威胁”“新挑战”“能力不足”“难以满足”“亟需提升”“瓶颈”“限制”“约束”“现有方法不足”等。后续通过实际运行和专家反馈动态沉淀经验模板。

14.6 的 agent 流程设计采用“模型 Orchestrator + 程序 Scheduler + 可复用 Worker + 分级 Context”的结构。核心原则是：Orchestrator 模型负责语义调度，程序 Scheduler 负责执行调度，Worker 是可复用能力模板，AgentRun 是 Worker 带上特定上下文后的一次执行实例。

基本关系为：

```text
Worker = 可复用能力单元
AgentRun = Worker + role_prompt + task_brief + context_pack + tool_scope + output_schema + trace_id
```

同一个 Worker 在获得不同角色提示词、任务 brief、上下文包和工具范围后，可以成为不同 agent。例如同一个 `reading_worker` 可以被实例化为 A 级信源阅读 agent、技术牵引线索阅读 agent、低空场景专题阅读 agent 或反证材料阅读 agent。

Orchestrator 模型负责：

- 理解用户目标或静默扫描触发条件。
- 生成 research brief。
- 拆分研究任务。
- 选择需要哪类 Worker。
- 为每个 Worker 生成任务级提示词、上下文包和输出要求。
- 查看 Worker 进度摘要。
- 判断是否扩检、补证、拆分需求、触发 debate、进入审核。
- 合并 Worker 结果，更新 registry、证据卡和 `CandidateDemand`。

程序 Scheduler 负责：

- 接收 Orchestrator 的派发指令。
- 创建任务队列。
- 控制并发、重试、超时和预算。
- 分配工具权限和信源范围。
- 记录 trace。
- 收集 Worker 输出。
- 向 Orchestrator 提供进度接口。
- 保证状态一致性、任务可恢复和执行可审计。

Orchestrator 派发任务时应提供：

- worker_type。
- task_objective。
- role_prompt_id 或 role_prompt。
- context_pack_refs。
- source_scope。
- tool_scope。
- output_schema。
- priority。
- budget。
- dependencies。
- stop_condition。
- trace_id。

Worker 进度接口不返回大段原文和冗长推理，而返回结构化进度摘要：

- status：running、blocked、completed、failed。
- partial_findings。
- new_evidence_cards。
- new_registry_entries。
- candidate_updates。
- open_questions。
- need_more_sources。
- risk_or_conflict。

Context 管理需要分级，支持 Worker 复用和 AgentRun 隔离：

- 持久角色层：长期有效的角色定位、能力边界、工具使用规则和输出规范。
- 任务约束层：由 Orchestrator 针对具体任务生成的 task brief、信源范围、预算、停止条件、输出 schema 和安全边界。
- 共享状态层：registry、`CandidateDemand`、证据卡、审核记录、trace 摘要等可跨 agent 共享的结构化状态。
- 运行观察层：Worker 在任务中接触到的正文片段、发现、反证、开放问题和中间判断。该层必须高度提炼，只把有意义的证据卡、候选更新、风险冲突和补证问题写回共享状态。
- 归档追溯层：完整原文、阅读片段、模型版本、prompt 版本、工具调用和运行日志，用于 trace 和复盘，不默认进入后续 agent 上下文。

程序应优化高吞吐、确定性和可缓存步骤；模型应处理语义判断和需求抽象。推荐分工为：

- 程序优先：信源采集、URL 去重、正文抽取、元数据抽取、关键词检测、BM25/向量检索、聚类、相似需求查重、任务队列调度、缓存、trace 记录、来源审计。
- 模型优先：文章需求线索判断、趋势/热点/痛点/需求分类、能力缺口抽象、技术牵引转需求假设、证据卡生成、反证/替代解释、过泛需求拆分、审核报告、最终调查报告。
- 混合处理：实体抽取、claim 抽取、证据强度初判、相关度 rerank。初期可由模型完成，后续根据成本和稳定性逐步规则化、小模型化或程序化。

检索式阅读应作为需求调研 worker 的基础工作流。它不是逐字阅读全文，而是先通过检索、页面结构和片段定位快速缩小阅读范围，再对关键材料回到原文证据片段。工作流为：

```text
研究目标 / 当前 claim / 待补字段
-> 生成多组检索问题和关键词
-> 搜索指定信源或白名单范围
-> 基于标题、摘要片段、来源等级、时间和栏目初筛
-> 打开高相关页面
-> 使用标题层级、摘要、导语、find、段落定位和引用区域快速定位相关片段
-> 抽取证据卡或反证卡
-> 交叉验证多个来源
-> 生成下一轮检索问题或停止建议
-> 写入 trace
```

该流程中，程序负责搜索、去重、排序、页面解析、片段定位、缓存和 trace；模型负责生成检索问题、判断片段相关性、提炼 claim、生成证据卡、提出反证方向和下一轮检索问题。这个流程也解释了系统为什么可以快速阅读大量网页：大多数页面只经过标题、摘要、结构和片段级阅读，只有关键证据来源才进入全文或重点章节精读。

工程实现路线已经收敛：一期不再把 LangGraph、GPT Researcher、OpenAI Agents SDK 作为并列候选底座，而是以 Python 复刻 Pi 的 AgentHarness 能力为主线，先交付一个可实际运行的需求挖掘 demo，再逐步补齐 Pi harness parity 和需求挖掘领域能力。

当前确定的主路线为：

```text
Pi AgentHarness 能力分析
-> Python harness kernel 复刻
-> fake provider 可运行 demo
-> 需求挖掘领域对象与工具接入
-> Responses / Codex provider adapter
-> Orchestrator / worker / scheduler 扩展
```

复刻对象不是 Pi 的完整 coding agent 产品，而是其通用 harness 能力：

- 低层 `AgentLoop`：负责 LLM turn、provider stream、工具调用、tool result 回填、steer/follow-up、`prepare_next_turn` 和事件序列。
- 上层 `DiscoveryHarness`：负责 phase 状态机、turn snapshot、pending proposal queues、save point、session/trace 持久化、context pack 重建、hook 和领域写入校验。
- Provider 层：首期保留 fake provider 和 OpenAI Responses / Codex-compatible adapter，不迁移 provider 全矩阵。
- Tool 层：复用 Pi 的 tool definition、schema 校验、并行/顺序执行、hook 拦截和输出截断思想。工具结果统一为 `content`、`details`、`domain_proposals`、`trace_proposals` 四个通道，其中 `details` 只保留程序/UI/debug 结构化结果，不承载待执行写入；工具集合改为检索、文档读取、证据卡、候选需求、审核和报告生成。
- Session/context 层：复用 append-only session tree、JSONL 持久化和 context projection 思路，但领域对象拆成 `DomainTraceStore`、`DomainStore`、`ContextPackBuilder`；运行时事件只进入 `EventBus` 或可选 runtime log，不作为正式报告证据。

实现语言以 Python 为主，放入 `src/knowledgegraph/demand_discovery/`，沿用当前仓库 `src/` 长期代码与 `tests/` 离线测试的组织方式。首个验收目标是 `scripts/demand_discovery_demo.py --mode fake` 可以在无网络、无 API key 的情况下跑通：fake provider 触发工具调用，harness 在 save point 写入 trace 和领域对象，最后输出最小需求报告摘要。

LangGraph、GPT Researcher、OpenAI Agents SDK 不作为一期实现底座，但仍可作为后续参考：

- LangGraph 可参考状态图、人机协同和长期编排思想。
- GPT Researcher 可参考 deep research 的 planner、source tracking 和 report publisher 形态。
- OpenAI Agents SDK 可参考 handoff、tracing、工具编排和轻量 agent API。

这些成熟实现的价值是校准工程实践，而不是替代本项目的 Python Pi Harness 复刻路线。具体实施计划见 `pi_harness_python_replication_implementation_plan.md`，文件级复用判断见 `pi_agent_harness_file_reuse_analysis.md`。

方法论上可吸收 Horizon Scanning。它适合作为需求挖掘上游机制：广泛扫描指定信源，捕捉 weak signal，聚类成主题簇，识别趋势、痛点、新能力空间或残余缺口，再进入 `raw_signal -> researchable_signal -> candidate_demand` 流程。Horizon Scanning 不直接生成正式需求报告，而是提供持续扫描、弱信号发现、主题聚类和机会/风险初筛能力。

在本项目中，Horizon Scanning 的含义持续扫描公开军事需求信源，捕捉早期变化信号，识别哪些信号值得进入需求挖掘流程。

其基本步骤为：

1. Scoping：明确扫描范围、白名单信源、关注主题、时间范围和排除边界。
2. Scanning：持续采集指定来源中的弱信号，包括新任务、新威胁、新作战样式、装备现状变化、能力短板、技术成熟迹象和残余缺口线索。
3. Signal Capture：将单篇资料中的线索记录为 signal，而不是直接写成需求。
4. Tagging：标注 signal 类型、来源等级、主题、潜在机会/风险、可能影响领域和不确定性。
5. Clustering：把分散 signal 聚合为主题簇，识别是否存在重复出现的场景变化、能力缺口或新能力空间。
6. Sensemaking：由模型和必要的人工判断共同分析主题簇的意义，决定进入 `researchable_signal`、`weak_signal`、`discarded_signal` 或 `candidate_demand`。
7. Monitoring：对暂时不成熟但有价值的 weak signal 保留复查条件，在新证据、新场景或新技术成熟信号出现时重新触发。

Horizon Scanning 产物不是正式需求，而是 signal registry 和主题簇。建议 signal 记录至少包含：

- signal_id。
- 来源与 source_tier。
- signal_type：趋势、痛点、技术热点、方案设想、反证/限制等。
- 主题关键词。
- 原始片段或摘要。
- 新颖性初判。
- 潜在影响方向。
- 不确定性。
- 建议动作：观察、补证、扩检、合并、淘汰、升级为 `researchable_signal`。

在军事装备需求挖掘场景中，Horizon Scanning 的价值是让系统持续感知“变化正在发生”，但不急于下结论。只有当 signal 被聚类、补证并能落到任务场景、能力状态差距或新能力空间时，才进入候选需求分析。

## 7. 证据与可信度共识

证据数量硬约束需要通过实际调研后确定，当前不宜过早规定“必须几条证据”。但每个候选需求必须能说明证据如何支持结论。

为了避免 debate 阶段占用过多上下文，建议使用证据卡片，而不是直接向审核 agent 塞入大段原文。

证据卡片是 claim 级别的可追溯证据单元，不是原文摘抄集合。证据卡片应说明某条资料支持、限制或反驳了什么判断，并能回到原文位置。

证据卡片、候选需求、来源记录和 trace 分离建模：

```text
CandidateDemand 表达“这个需求判断是什么”
EvidenceCard 说明“哪些 claim 支撑、限制或反驳这个判断”
SourceRecord 说明“证据来自哪里”
DomainTraceEvent 说明“这个判断和证据是如何被发现、修改、审核和引用的”
```

核心关系为：

```text
CandidateDemand 1 -> N EvidenceCard
SourceRecord 1 -> N EvidenceCard
CandidateDemand 1 -> N DomainTraceEvent
EvidenceCard 1 -> N DomainTraceEvent
```

第一版数据对象保持精简：

```yaml
CandidateDemand:
  candidate_id: string
  title: string
  demand_statement: string
  status: enum(raw_signal, researchable_signal, weak_signal, discarded_signal, candidate_demand, demand_report, human_reviewed)
  evidence_ids: string[]
  open_questions: string[]
  solution_signals: string[]
  created_by: string
  created_at: datetime
  updated_at: datetime
```

`CandidateDemand` 是 agent 协作和审核的主对象。`demand_statement` 承载完整需求语义，不把任务场景、触发因素、能力缺口、现有能力状态、目标能力状态、不确定性等全部固化为独立字段。这些被删除的字段并非无意义，而是作为填写 `demand_statement`、生成 `open_questions`、编写审核报告和设计角色 prompt 时的思维框架。
`status` 的枚举值必须与候选状态机保持一致；对模型开放的 `create_or_update_candidate` 工具 schema 应直接暴露这些枚举值，不能只写成自由字符串。模型可能使用 `proposed`、`draft` 等自然语言近义词，但这些词不属于领域状态；实现层可做兼容归一或返回可恢复工具错误，不能把未知状态写入 save point。

```yaml
EvidenceCard:
  evidence_id: string
  source_id: string
  claim: string
  evidence_summary: string
  excerpt: string | null
  source_location: string
  evidence_assessment: string
  created_by: string
  created_at: datetime
```

`EvidenceCard` 不依赖 `CandidateDemand` 存在。证据可能先于候选需求被发现，也可能被多个候选需求复用。候选需求通过 `evidence_ids` 引用证据卡。`claim` 是证据卡核心，负责表达这条证据说明什么；支持、反证、限制、背景等关系应体现在 `claim` 和 `evidence_assessment` 中，而不是强制拆成多个字段。`evidence_assessment` 用自然语言说明证据可信度、适用范围、局限性、是否二手转述、是否需要交叉验证等。

```yaml
SourceRecord:
  source_id: string
  title: string
  source_name: string
  source_tier: enum
  source_type: enum
  publish_time: datetime | null
  url_or_path: string
  summary_text: string | null
  summary_source: enum
  collection_decision: enum
  author_or_org: string | null
  is_repost: bool | null
  original_source: string | null
  institutional_stance: string | null
  created_at: datetime
  updated_at: datetime
```

`SourceRecord` 是资料级来源审计对象，不承担 claim 判断。

```yaml
DomainTraceEvent:
  domain_trace_id: string
  trace_id: string
  event_type: enum
  actor: string
  target_type: enum
  target_id: string
  input_refs: string[]
  output_refs: string[]
  summary: string
  decision: string | null
  rationale: string | null
  model: string | null
  prompt_id: string | null
  tool_refs: string[]
  runtime_event_id: string | null
  created_at: datetime
```

`DomainTraceEvent` 由 runtime 维护，只记录领域状态变化和报告溯源链，例如来源读取、证据卡创建、候选需求创建/修改/合并/回退、审核结论和报告生成。runtime 自动记录时间、actor、target、input_refs、output_refs、工具调用、模型、prompt_id 和状态变化；agent 只提供结构化语义摘要、decision、rationale、new_questions 或 suggested_actions；人工审核动作由系统 UI 或人工录入接口写入 domain trace。agent 不决定是否记录 domain trace，避免溯源缺口。

运行时事件与领域 trace 保持轻量分层：

```text
RuntimeEvent：provider_stream、agent_runtime、harness、scheduler；用于 UI、进度、debug 和调度，不作为正式报告证据。
SessionEntry：消息、save point、active pointer、模型/工具变化；用于会话恢复和 replay，不直接作为报告证据。
DomainTraceEvent：source -> evidence -> candidate -> audit -> report 的领域因果链；用于来源审计、报告溯源、人工审核和后续 SOP/skill 沉淀。
```

首版不为 provider、agent、harness、scheduler 分别建立独立持久化表。它们作为 `RuntimeEvent.category` 在事件总线中区分；只有 `DomainTraceEvent` 进入 `DomainTraceStore`。

拆分、合并、去重和相似性判断不进入 `CandidateDemand` 主字段，而作为 `DomainTraceEvent` 记录：

```text
candidate_split
candidate_merged
duplicate_checked
```

debate agent 默认阅读证据卡片；只有在需要核查时，再回取原文片段或全文。

“资料热度高”和“真实需求强”很难严格区分，不应作为一期核心难题。更可行的做法是明确标注来源、证据类型和不确定性，让用户或专家参与最终判断。

专家审核状态不应放在证据搜集阶段。它应出现在需求文档完成后，作为人工审核流程的一部分。

## 8. 评审量表与准入标准共识

评审量表是必要的，目的是让审核 agent 稳定判断什么样的线索可以进入正式需求报告，什么样的线索应被补证、降级、淘汰或保留观察。评审量表不必一开始精确量化，重点是形成可解释的准入标准和审核理由。

可讨论的评审维度包括：

- 军事或装备研发相关性。
- 任务场景清晰度。
- 威胁或对抗环境清晰度。
- 能力缺口明确程度。
- 现有方案未解决程度。
- 证据强度。
- 来源可信度。
- 新颖性。
- 技术路线可讨论性。
- 风险与约束清晰度。
- 是否值得进入人工评审。

审核 agent 应根据评审量表做结论判断，并生成审核报告用于溯源。审核报告至少应说明审核结论、关键理由、所依据的证据卡片、反证或限制条件、补证建议和状态流转建议。

评审量表不应设计成复杂分数模型。一期可采用检查清单方式，每个评审项输出：

```text
结论：通过 / 存疑 / 不通过
理由：简短说明
建议：通过、补证、降级或淘汰
```

核心评审项包括：

- 场景是否明确。
- 能力缺口或新能力空间是否明确。
- 证据是否可回溯。
- 是否只是普通趋势。
- 是否只是技术热点。
- 是否被写成方案、装备或技术口号。
- 如已有方案，是否仍存在残余缺口。
- 是否存在安全边界问题。

一票否决项应保持少量，仅用于会破坏流程质量或安全边界的情形：

- 无可回溯来源。
- 来源属于 D 级排除信源。
- 无法落到任何任务场景或潜在应用场景。
- 完全是技术、装备或平台方案口号，没有问题、缺口或新能力空间表达。
- 超出公开资料和安全边界。

以下情况不作为一票否决项，应触发补证、降级、拆分或保留观察：

- 证据数量少。
- 新颖性不明确。
- 需求粒度偏泛。
- 存在反证。
- 只有 B/C 级线索。

证据是否足够按 claim 判断，不按固定证据数量判断。审核 agent 需要判断：

- 支撑 `demand_statement` 的关键 claim 是否有证据卡。
- 关键证据是否能回到原文。
- 是否至少有非 C 级来源参与支撑。
- 是否记录了反证或限制条件。
- 证据是否只证明背景趋势，而没有证明能力缺口或新能力空间。

进入 `demand_report` 前的最低证据要求为：

- 至少一条非 C 级证据支撑核心 claim。
- 关键 claim 有可回溯原文片段。
- 如存在明显争议，需要记录反证或限制条件。
- 不能只依赖模型生成摘要或 C 级线索。

新颖性是需求调研中的分析维度，不是相对用户已知方向或当前资料库的去重指标。用户已知方向、当前资料库和已有 `CandidateDemand` 只用于查重、合并、避免重复选题和 registry 管理，不用于定义需求本身是否新颖。

新颖性判断角度包括：

- 场景新颖性：出现新的任务场景、使用环境、对抗条件或应用对象。
- 缺口新颖性：暴露过去未充分讨论的能力缺口或残余缺口。
- 触发新颖性：由新威胁、新约束、新技术可行性或新组织方式触发。
- 组合新颖性：已有技术、能力、场景之间出现新的组合关系。
- 重要性变化：旧问题因环境变化、对抗变化或装备演进变得更关键。
- 应用形态新颖性：新技术或新场景带来新的能力组织方式或使用形态。

新颖性不作为候选需求成立的必要条件。需求成立主要看场景、缺口、证据和边界；新颖性影响优先级、报告重点和是否值得专题深挖。

进入人工评审的最低门槛为：

- 有明确 `demand_statement`。
- 不是纯趋势、热点或方案口号。
- 至少有一个任务场景或潜在应用场景。
- 至少有一个能力缺口、新能力空间或残余缺口。
- 至少有可回溯证据。
- 审核 agent 没有触发一票否决项。

审核结论可影响静默推送优先级：

- 通过 + 高新颖性 + 高影响：立即推送。
- 通过 + 中等价值：进入周期性摘要。
- 需补证：不推送，进入补证队列。
- `weak_signal`：进入观察池。
- `discarded_signal`：不推送。
- `watchlist`：有新证据时再推送。

## 9. 输出形态共识

最终输出应偏调查报告，类似需求分析师给出的结果，而不是纯技术方案书。

单个需求报告建议包含：

- 需求标题。
- 需求类型：显式需求或推断需求。
- 核心结论。
- 任务场景。
- 威胁或对抗环境。
- 能力缺口。
- 现有解决方案及未解决问题。
- 支撑证据。
- 反证或限制条件。
- 相关技术方向。
- 风险约束。
- 待验证问题。
- 后续建议。
- 来源审计。
- 调研日志。

不建议要求模型输出内部思维链。更合适的要求是输出可审计论证链，即明确说明“哪些证据支持了哪些判断、哪些判断是推断、哪些地方仍不确定”。

补充资料不应只作为报告后的下一步。更合理的流程是，在 debate 或审核阶段发现证据不足时，就触发补充检索、原文阅读或相关资料扩展。最终报告中的“后续建议”主要面向用户或专家继续确认，而不是替代系统自身的补证步骤。

最终报告采用“强约束骨架 + 弹性论证空间”。一级结构、证据、边界和溯源必须稳定；具体论证组织、洞察表达、需求成因分析、残余缺口分析和相关方案线索归纳可以由模型根据材料灵活组织。

报告主线必须围绕需求本身：

```text
需求是什么
为什么成立
证据是什么
不确定性是什么
相关方案线索如何服务这个需求
```

报告不设置 `Signal Brief` 作为正式报告类型。过程中的高价值信号不新增独立 `SignalRecord` 业务实体，而通过 `SourceRecord`、`EvidenceCard`、`DomainTraceEvent` 和 registry/任务队列视图管理。只有当 agent 能形成初步 `demand_statement` 时，才创建 `CandidateDemand`。

正式报告类型先保留两类：

- `Candidate Demand Report`：面向 `candidate_demand`，用于提交人工评审的正式候选需求报告。
- `Deep Demand Analysis`：面向高优先级、已通过或修改后通过的需求，进行更深交叉验证、方案残余分析、候选课题和应用场景推演。

多来源综合形成的方案线索、技术路线、参数化设想、装备形态假设或模拟应用场景可以出现在报告中，但必须作为“相关方案线索/候选实现设想/应用场景推演”等附属分析栏目，不替代需求主结论。报告需要明确区分公开来源事实、模型综合推断和待验证假设，并保留输入来源、推理依据、适用条件、不确定性和待验证问题。

公开资料中的参数、指标、实验条件和性能表述可以作为 `EvidenceCard` 或方案线索记录。系统可以分析这些内容说明了什么能力、约束、残余缺口或应用空间；是否需要额外安全审查应放在审核 agent 和报告生成阶段处理，不应在所有 worker prompt 中加入冗长限制。

## 10. 评估与验收共识

模块价值主要体现在两方面：

- 提出可讨论的需求假设。
- 节省人的资料搜集、阅读、归纳和初步研判时间。

评测指标可以优先关注：

- 是否命中关键缺口。
- 人工判断解释质量。
- 是否能节省调研时间。
- 证据链是否可审计。
- 是否能区分需求、普通趋势和技术热点。
- 是否能保留反证和不确定性。

gold case 的制定有价值，需要和甲方或老师讨论。gold case 可以用于检验系统是否能从指定资料中发现专家认为关键的能力缺口或需求假设。

Gold/Silver Case 的构建可以参考成熟 deep research 工具，但不直接把外部系统输出作为真值。成熟 deep research 输出更适合作为 reference baseline，用于发现线索、补充来源、对照报告质量和构建 CaseDraft。

推荐 case 构建思路：

```text
同一选题
-> 多个成熟 deep research 工具 + 本地系统分别调研
-> 收集可见研究计划、可见检索路径、引用网页、证据片段、最终回答和本地系统输出
-> 本地系统将多系统输出规范化为 CaseDraft
-> 人工审核和修订
-> Silver Case / Gold Case
```

本地系统在该流程中的职责是 case 规范化，而不是直接判定真值。它应将不同系统的模型输出、可见研究过程、搜索网页、引用资料和本地结果整理为可人工评审的结构化 case 内容，包括需求点、能力缺口、相关技术/方案线索、引用来源、证据片段、一致/冲突点和待专家确认问题。

Case 的具体字段 schema 暂不在当前阶段固化。后续在完成成熟 deep research 实现调研和本地系统初版实验后，再根据实际输出形态和评测需要确定字段。

`negative_cases` 不作为第一版必填项。负样本、驳回点和争议点可从人工审核过程自然沉淀，例如哪些点只是趋势/热点、哪些点证据不足、哪些点不应算需求。第一版可先保留 conflicts/open questions 和人工驳回记录，后续再抽象为负样本集。

## 11. 需求、趋势、热点和伪需求的区分共识

需求挖掘模块需要区分真实需求、伪需求、普通趋势和技术热点。该区分的目的不是做概念分类本身，而是定义线索升级为候选需求的门槛。

四类概念可先采用以下工作定义：

- 真实需求：趋势、痛点或技术可能性落到具体任务后，形成明确能力缺口或新能力空间，并有证据支撑。
- 伪需求：看起来像需求，但没有完成从现象到能力缺口的论证，或提前写成技术、装备、平台、系统等方案陈述。
- 普通趋势：外部环境、政策、任务、装备、技术、对抗或组织方式的变化。
- 技术热点：某类技术快速发展、受到关注、被频繁报道或被认为具有潜在价值。

普通趋势本身不是需求。普通趋势只有在满足以下链路时，才可以升级为候选需求：

```text
趋势变化
-> 影响某类任务/装备/场景
-> 造成现有能力不适配，或打开新的能力空间
-> 形成可证据化的能力缺口或需求假设
```

技术热点也不能直接转成需求。技术热点只有在说明“改变了什么能力可行性、对应什么任务场景、解决或创造了什么需求空间”后，才可以进入候选需求分析。

技术热点转化为需求主要有两条有效路径：

```text
某技术成熟
-> 过去做不到的能力现在可能做到
-> 某类场景可以出现新的应用形态
-> 形成候选需求
```

```text
某技术被广泛提出
-> 但在特定环境/约束下仍不够
-> 暴露新的工程、性能、可靠性或适配缺口
-> 形成技术需求或残余缺口需求
```

缺少任务场景或威胁环境的线索不应直接淘汰，但不能进入正式候选需求。可分为三档处理：

- 可补全线索：缺少场景或证据，但可以通过进一步检索补齐。
- 弱线索：有一定价值，但暂时无法定位场景、缺口或应用价值。
- 淘汰线索：只有口号、热点或孤立观点，补证后仍无法落到任务场景和能力状态。

已有方案存在时，不应直接判定需求已被解决。需要检查是否存在残余缺口：

- 场景残余：方案只适用于部分场景。
- 性能残余：指标、稳定性、响应、精度等仍不足。
- 约束残余：成本、体积、能耗、维护、部署、可靠性等限制明显。
- 体系残余：单点技术可行，但难以融入实际体系或流程。
- 证据残余：方案只是概念、演示或局部验证，缺少真实环境证据。

可采用以下判断门禁决定线索是否进入候选需求：

```text
1. 这是趋势、热点、痛点，还是已经是需求陈述？
2. 是否能定位到任务场景或潜在应用场景？
3. 是否能说明现有能力状态与目标能力状态的差距？
4. 是否有证据证明这个差距值得关注？
5. 如果已有方案，是否仍存在残余缺口？
6. 能否写成问题/缺口陈述，而不是技术/方案陈述？
```

只有通过上述门禁的线索，才进入候选需求；否则应降级为背景趋势、技术观察、待补证线索或伪需求。

## 12. 候选需求对象与状态流共识

需求挖掘模块不应从原始资料直接跳到正式需求报告。中间应设置 `CandidateDemand` 作为线索到报告之间的工作单元，用于承载场景、触发因素、能力状态差距、证据、不确定性和相关技术线索。

需求相关概念在数据结构中分为三层：

- 核心字段：需求陈述、任务场景、触发因素、能力缺口或新能力空间等，用于支撑候选需求是否成立。
- 标签字段：新需求、潜在需求、显式需求、推断需求、痛点驱动、场景驱动、技术牵引、残余缺口等，用于描述需求来源、确定性和类型。
- 下游栏目：技术需求、技术创新方向、已有方案线索等，用于承接需求分析后的派生研判，不替代主需求结论。

其中，痛点更适合作为原始线索字段或触发因素字段，不作为需求类型。技术需求作为能力缺口向解决路径过渡的派生分析栏目。技术创新方向作为下游输出或附属研判栏目，可服务于预研选题，但不与需求本体平级。

`CandidateDemand` 的建议最小字段见“证据与可信度共识”。主对象保持简洁，需求分析维度不固化为字段。原始线索类型、触发类型、缺口类型、任务场景、现有能力状态、目标能力状态、不确定性等维度用于 prompt、审核量表、证据卡 claim 和审核报告，引导 agent 思考与审核，而不是全部落成 `CandidateDemand` 主字段。

原始线索类型建议固定枚举：

- `trend_signal`：普通趋势。
- `tech_hotspot`：技术热点。
- `pain_point`：痛点现象。
- `explicit_demand`：显式需求。
- `solution_concept`：已有方案设想。
- `evidence_counterpoint`：反证或限制线索。

触发类型建议固定枚举并允许多选：

- `pain_driven`：痛点驱动。
- `scenario_driven`：场景驱动。
- `technology_pulled`：技术牵引。
- `residual_gap`：残余缺口。
- `threat_driven`：威胁或对抗驱动。
- `constraint_driven`：约束驱动。

缺口类型建议固定枚举并允许多选：

- `capability_gap`：能力缺口。
- `scenario_gap`：场景适配缺口。
- `performance_gap`：性能缺口。
- `constraint_gap`：约束缺口。
- `system_integration_gap`：体系或集成缺口。
- `evidence_gap`：证据缺口。
- `new_capability_space`：新能力空间。
- `new_application_space`：新应用形态空间。

线索不应简单二分为“是需求/不是需求”，而应使用状态流管理：

```text
原始资料
-> 线索
-> 可补全线索 / 弱线索 / 淘汰线索
-> 候选需求
-> 需求调查报告
-> 人工审核
```

可先采用以下状态定义：

- raw_signal：原始资料中发现的趋势、热点、痛点、方案设想或显式需求。
- researchable_signal：有潜力，但缺少场景、证据或缺口，需要补充检索。
- weak_signal：有一定参考价值，但暂时不能形成需求。
- discarded_signal：口号、孤立观点、纯热点、无场景或无证据，暂不进入后续。
- candidate_demand：已能说明场景、能力状态差距、证据和不确定性。
- demand_report：经补证、debate 和审核后形成的正式调查报告。
- human_reviewed：用户或专家给出采纳、驳回、修改、保留观察等结论。

状态机不是线性流水线，而是可迭代的 agent loop。agent 应能在流程中自发发现字段缺失、证据不足、分类错误或粒度不合适，并触发补证、原文阅读、合并拆分、改写、降级或淘汰。

基本 agent loop 为：

```text
线索发现
-> CandidateDemand 草稿
-> 字段完整性检查
-> 补证 / 原文阅读 / 合并拆分 / 重写
-> 可选 debate
-> 审核 agent 审核
-> 通过进入 report，未通过则回退、降级或淘汰
```

`candidate_demand` 进入 `demand_report` 前不强制全部经过 debate。debate 是可选的挑战机制，不承担最终审核职能。最终门禁由审核 agent 根据评审量表完成。

debate 的职责是：

- 检查候选需求是否只是趋势或热点。
- 寻找反证和替代解释。
- 判断已有方案是否已经充分解决。
- 指出证据断点。
- 提出补证问题。
- 建议合并、拆分、降级或改写。

debate 输出 `debate_summary` 和补证建议，不输出最终通过或不通过结论。

以下情况应触发 debate：

- 推断需求。
- 技术牵引型需求。
- 新颖性高但证据弱。
- 证据之间存在冲突。
- 已有方案是否充分解决存在争议。
- 准备生成高优先级正式报告。

显式需求、证据强且低争议的候选，可以直接进入审核 agent。

人工审核状态建议记录为：

- `pending_review`：待人工审核。
- `approved`：通过。
- `approved_with_changes`：修改后通过。
- `needs_revision`：需要修改。
- `rejected`：驳回。
- `watchlist`：保留观察。

人工审核记录至少包括：

- reviewer。
- review_time。
- decision。
- decision_reason。
- accepted_claims。
- rejected_claims。
- requested_changes。
- notes。

最终 report 如果被通过，必须带有可溯源 trace。trace 用于后续复盘、SOP 沉淀或 skill 抽象，但不自动生成 SOP 或 skill，是否沉淀由开发者决定。

trace 至少包括：

- trace_id。
- 用户原始输入或触发来源。
- 检索计划。
- 检索关键词和来源范围。
- 阅读过的资料。
- 证据卡片。
- `CandidateDemand` 修订历史。
- 补证动作。
- debate_summary。
- 审核 agent 审核报告。
- 最终人工审核记录。
- 模型、prompt 和工具版本。

用户报告中不必展示全部 trace，可以展示来源审计与论证链摘要；完整 trace 存为附录或结构化记录。

残余缺口不单独作为最终需求类型，而应作为触发类型或缺口类型标注。一个候选需求可以同时具有多种标签，例如“技术牵引 + 残余缺口”“场景驱动 + 性能残余”“痛点驱动 + 体系残余”。

残余缺口可先拆为：

- 场景残余。
- 性能残余。
- 约束残余。
- 体系残余。
- 证据残余。

需求粒度不在生成阶段强行限制，而在审核阶段处理。审核 agent 需要判断：

- 是否过泛：只有大方向，没有具体场景和缺口。
- 是否过碎：只是单一参数、单一部件或单一现象，无法形成独立需求。
- 是否重复：与已有候选需求在场景、缺口和证据上高度重叠。
- 是否存在上下位关系：一个是体系级需求，另一个是分系统、部件或技术侧派生需求。

审核 agent 可据此提出合并、拆分、去重或层级归并建议。

状态池的存储与复查规则先采用轻量设计：

- `researchable_signal`：保留缺失字段、补证方向、下一步检索问题和已有证据卡。
- `weak_signal`：保留摘要、来源、弱点原因和可触发复查的条件。
- `discarded_signal`：只保留最小审计信息和淘汰原因，避免重复处理。
- `candidate_demand`：保留完整结构、证据卡、审核记录和状态流转记录。

`weak_signal` 仅在出现新证据、新场景、新技术成熟信号，或用户主动触发相关主题时复查。`discarded_signal` 默认不复查，除非用户明确要求，或同主题重复出现高质量新证据。

## 13. 安全与边界共识

数据主要来自公开资料和授权资料。

需求分析本身可以涉及具体武器设计、作战实施细节或参数优化方案。但系统应该以高层的装备形态需求、能力方向或作战方式变化假设等方向分析为主。

需要保留：

- 来源审计。
- 报告留痕。
- 调研日志。
- 模型调用记录。

模型调用可以使用 API。报告以本地查看为主。

一期报告默认在本地工作区查看，不做外部自动分发。允许用户主动导出 Markdown、PDF 或 HTML；系统不应自动推送到外部平台、公开链接或第三方协作工具。后续如需接入企业知识库或协作平台，应单独设计权限与发布流程。

调研日志和模型调用记录采用分层保留：

- 长期保留：`SourceRecord`、`EvidenceCard`、`CandidateDemand`、`DemandReport`、审核报告、人工审核结论和 trace 摘要。
- 中期保留：worker 运行摘要、检索 query、expansion 记录、debate_summary、prompt_id、model、tool_refs。
- 短期或按需保留：大段原文缓存、页面快照、中间片段、失败重试日志、冗长模型输入输出。

具体保留时长不在当前阶段固定，应实现为配置项。原则是保留支撑复盘、审计和报告重建的内容，允许清理纯中间过程、重复内容和超大文本缓存。

来源审计使用结构化记录保存，而不是只放在报告末尾。完整审计由 `SourceRecord`、`EvidenceCard`、`DomainTraceEvent` 三层共同支撑。报告中只展示简化来源信息，例如来源名称、标题、发布时间、来源等级、引用位置和证据摘要；完整审计保存在结构化记录中，用于回看原文、检查证据是否支撑 claim、复现报告生成过程、人工审核和后续构造 Silver/Gold Case。

人工评审前候选内容需要状态管理：

- `draft`：内部草稿，agent 生成，未审核。
- `review_ready`：证据和 trace 基本齐全，可交人工评审。
- `approved`：人工审核通过。
- `rejected`：人工审核驳回。
- `watchlist`：保留观察。

可增加 `sensitive_review_required` 标记。该标记不表示内容不能写，而是表示需要人工重点审核。触发场景包括候选装备形态、模拟应用场景、参数/指标类来源表述、模型综合方案设想，以及高不确定性但影响较大的判断。
