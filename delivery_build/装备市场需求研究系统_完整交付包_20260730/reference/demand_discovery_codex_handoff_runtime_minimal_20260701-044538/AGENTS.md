# AGENTS.md

本文件是给在 `D:\amyproject\knowledgegraph` 下工作的 agent 使用的长期操作规范。它只规定工作方式、输出要求、目录定位和安全边界；具体项目内容以 `docs/` 下的专题文档为准。

## 1. 适用范围与指令优先级

### 1.1 适用范围

- 本文件适用于本仓库内的文档整理、架构设计、调研材料维护、脚本开发、数据采集和后续可能新增的产品代码。
- 不要把 `AGENTS.md` 当作项目设计正文。项目定位、架构细节、技术选型和调研结论应写入 `docs/` 下的正式文档。
- 若新任务与既有文档约定冲突，不要自行覆盖约定；先说明冲突、影响范围和建议处理方式。

### 1.2 指令优先级

工作时按以下顺序处理约束：

1. 当前会话中的系统、开发者和用户明确要求。
2. 本仓库 `AGENTS.md`、一级目录 `README.md` 和相关项目文档。
3. 当前任务直接相关的 spec、设计文档、调研材料和代码注释。
4. 可用 skill / Superpowers / MCP 工具流程。

若本文件与更高优先级指令冲突，遵循更高优先级指令。

## 2. 工作入口与目录规则

### 2.1 工作入口

进入本目录后，先阅读：

1. `docs/README.md`
2. 当前任务所属一级目录的 `README.md`
3. 当前任务直接相关的 spec、源材料或脚本

只读分析任务可以直接处理；涉及文件修改、目录调整、脚本执行或长期规范变更时，先明确目标、边界、风险和验证方式。

### 2.2 目录定位

```text
docs/
  README.md                    # 文档索引
  architecture/                # 架构设计文档
  research/                    # 调研方向与深度调研报告
  source-materials/            # 原始需求参考
  technology-selection/        # 技术选型文档
data/                          # 数据采集、原始材料和处理中间产物
scripts/                       # 可复用脚本和流程工具
web/                           # 网页交互、采集关键元素和浏览器相关资料
```

新增长期文档时，按主题放入 `docs/` 下对应目录，并同步更新 `docs/README.md`。新增、移动、删除一级目录内的重要文件时，应同步更新该一级目录的 `README.md`。

### 2.3 一级目录 README 约定

项目只在一级目录维护 `README.md` 作为导航页和边界说明。一级目录指仓库根目录下的直接子目录，例如 `docs/`、`data/`、`scripts/`、`web/`，以及后续可能新增的 `src/`、`tests/`、`configs/`。

一级目录 `README.md` 的作用：

- 说明该目录为什么存在。
- 汇总该目录下子目录和关键文件的用途。
- 说明该目录内文件的边界约束和维护规则。
- 说明新增、移动、删除文件时需要同步更新的索引或说明。
- 记录该一级目录内不允许破坏的约定。

agent 在修改文件前应先查找所属一级目录的 `README.md`。完成代码修改、文档移动、目录重组或新增重要文件后，必须同步更新受影响一级目录的 `README.md`。

未经用户许可，不得破坏一级目录 `README.md` 中已经声明的约定；如必须调整，应在回复中说明原因、影响范围和新的约定。不要新建深层 README，除非用户明确要求。

### 3.1 搜索与读取

- 不确定文件位置时，优先使用 `rg --files`。
- 精确查找已知字符串时，使用 `rg` 或等价快速搜索。
- 需要理解架构、调用链、数据流、入口、依赖关系或自然语言定位代码时，优先使用 fast-context。
- 独立的只读文件读取、搜索和状态检查可以并行执行。

### 3.2 文件编辑

- 修改文件使用 `apply_patch`。
- 不要用临时脚本或 shell 拼接写文件，除非是格式化、生成产物或批量机械处理且有明确理由。

### 3.3 浏览器 MCP

- 前端实现、页面搭建、交互流程、表单填写、回归验证、批量重复操作：优先使用 Playwright MCP。
- 页面状态分析、DOM/样式检查、Console 报错、Network 请求、Performance 分析、现有浏览器会话调试：优先使用 chrome-devtools MCP。
- 如果任务描述不明确，先用 chrome-devtools 做诊断；只有在需要脚本化复现、自动化操作或回归验证时，再切换到 Playwright。
- 除非用户明确要求，否则不要在同一个短任务里混用两个浏览器 MCP。
- 如果用户明确点名某个 MCP，严格按用户要求执行。

## 4. 任务分流与流程选择

### 4.1 只读任务

分析、解释、架构说明、代码阅读、纯信息型问答和只读审查可直接处理。结论必须清晰、可追溯，并明确区分事实、来源声明、推断、假设和待验证问题。

真实 bug 排查但尚未进入修改时，先确认现象、触发条件、影响范围和根因，再提出修复或进入实现。

### 4.2 轻量修改

轻量任务包括单文件或小范围修改、明确 bug 修复、局部文档调整、配置或文案更新、小测试补充。

默认采用满足质量要求的最短路径：直接定位、修改、定向验证。只有在目标、边界或风险无法从当前上下文判断时才提问。轻量任务不强制生成独立 spec 或 plan 文件。

### 4.3 中大型任务

以下情况应升级为更明确的计划或阶段化执行：

- 影响公共 API、schema、持久化、共享类型、根配置、CI、依赖或跨模块契约。
- 需要目录重组、大范围重构或多文件协同修改。
- 需求仍不清晰，或验收标准会影响实现路径。
- 验证范围明显超过定向验证。

多步任务优先维护可见任务列表；任一时刻只保留一个进行中的主步骤。

### 4.4 流程升级与降级

- 升级到更重流程：影响范围超出初始判断、涉及公共 API/schema/持久化/共享逻辑、需求仍不清晰、验证覆盖不足、任务演变为中大型实现或重构。
- 降级到更轻流程：改动局部且边界清晰、不涉及共享核心逻辑、验证直接、补长计划或补测试的成本明显高于收益。

## 5. Superpowers 与 Skills

默认以 Superpowers 作为主工作流体系，但不默认启用 full Superpowers。本文件保留本仓库的轻重分流、环境约束、交付偏好和沟通方式；具体某个 skill 是否启用，以当前任务规模、当前会话可用 skill 和更高优先级指令共同决定。

若 skill 流程与用户明确要求、本仓库约定或当前会话更高优先级指令冲突，遵循更高优先级约束。

### 5.1 技能（Skills）

- 技能存放位置：
  - 普通 Codex skill：`~/.codex/skills/<skill-name>/SKILL.md`（个人）与 `.codex/skills/<skill-name>/SKILL.md`（项目共享，可选）。
  - Superpowers skill：通常位于 `~/.codex/superpowers/skills/<skill-name>/SKILL.md`，不要按 `.codex/skills/superpowers/...` 拼接路径。
  - 实际可用 skill 与路径以当前会话提供的 skills 列表为准；命中 skill 时优先读取列表中给出的 `file:` 路径。
- 开始任务前，应优先判断是否命中对应 skill；命中时阅读 `SKILL.md` 并按流程执行。
- 本文件默认采用以下主干整合方式：
  - 实现前：`brainstorming -> writing-plans`
  - debug：`systematic-debugging`
  - review：`requesting-code-review` / `receiving-code-review`
  - 完成前：`verification-before-completion`
  - 高风险行为变更：`test-driven-development`
  - 前端设计：`ui-ux-pro-max`
- 本地个人工作流 skill 可保留私人默认路径、私人笔记目录与本机脚本入口；若对外发布，必须基于单独副本做脱敏，不直接公开 `~/.codex/skills/` 源文件。
- 调研总结 / 输出笔记：`research-note-wrap`
- 会话收尾：`session-wrap`
- 提交总结 / 日报：`commit-daily-summary`
- 项目级日报：`project-daily-summary`
- worktree / branch / parallel 收口：`worktree-closeout`
- 并行开发规划 / 多 worktree 协作：`codex-parallel-collab`
- 在回复中声明本次使用了哪些技能。

### 5.2 轻量任务中的 skill 使用

- 轻量任务可跳过完整 `brainstorming`、`writing-plans`、`using-git-worktrees` 和重 review 链，直接实现并做定向验证。
- 轻量任务首次最多问 1 个关键问题；若已有上下文足以判断，直接说明假设并推进。
- 轻量任务不强制生成独立 spec、plan 或长期文档，除非用户明确要求、项目规范要求或确有长期协作价值。

## 6. 文件修改与工程规范

### 6.1 文件修改规范

- 先定位上下文，再修改文件。
- 修改前确认任务目标、影响范围和输出形态。
- 不移动、删除或重命名文件，除非用户明确要求或这是完成任务必需的一部分。
- 移动文件后必须更新相关索引和路径引用。
- 不还原用户未要求还原的改动。
- 不把源材料、初版方案、抽取候选或模型推测直接写成最终事实。
- 修改某目录下文件时，遵守所属一级目录 `README.md` 中的定位和边界。
- 修改完成后，检查是否需要同步更新所属一级目录 `README.md`。

### 6.2 代码与脚本规范

当前项目以文档、设计和数据采集脚本为主，正式产品代码目录尚未固化。

后续如需新增正式代码：

- 先确认模块边界、输入输出和实施计划。
- 建立清晰目录，例如 `src/`、`tests/`、`configs/`、`scripts/`。
- 优先局部修改和最小充分实现，避免无关扩张。
- 保持函数、文件和模块职责清晰，避免深层嵌套、魔法数字和隐式副作用。
- 测试优先覆盖关键路径、边界情况和错误路径。
- 自动抽取、LLM 输出、图谱写入等关键流程必须保留来源、证据、版本和执行记录。
- 不把配置密钥、API Key 或本地私有配置写入仓库。

## 7. 并行与子任务

优先并行处理互不依赖的只读搜索、文件读取和检查。并行写入或子代理拆分只适合边界清晰、写入范围不重叠、可独立验证的任务。

除非当前会话规则允许且用户明确要求或授权，不主动派发子代理。需要并行协作时，应先明确每个子任务的 `scope_read`、`scope_write`、验证方式和阻塞条件；默认禁止两个子任务修改同一文件、同一 shared contract、同一 schema、同一根配置或同一入口文件。

子任务完成不等于整体完成。收尾时必须检查冲突面、依赖关系、整合顺序和最终验证。

## 8. 验证与交付门禁

不得虚构已运行命令、退出码或验证结果。没有验证证据，不得声称“通过”“完成”“可提交”或“可合并”。

结束任务前检查：

- 是否回答了用户最新请求。
- 是否修改了正确文件。
- 是否需要更新受影响一级目录的 `README.md`。
- 是否存在失效路径或移动后的旧引用。
- 是否误把源材料、抽取候选或推测内容写成事实。
- 是否完成与本次改动直接相关的验证。
- 若关键验证无法执行，是否说明原因、影响和剩余风险。

## 9. 安全边界

- 不运行破坏性命令，例如 `git reset --hard`、不受控递归删除等，除非用户明确要求并确认范围。
- 不使用非 Git 工具直接操作 `.git`。
- 不终止非当前任务启动的进程，除非用户明确要求。
- 不将密钥、凭证、API Key 硬编码进源码或文档。
- 不用不可信输入拼接 shell 命令、SQL 或危险文件路径。
- 数据库访问必须使用参数化查询。
- 所有涉及公开资料、装备研发、技术路线和产品形态的输出都保持在公开资料、高层分析、方向研判和专家评审层面。

## 10. 输出与提交规范

### 10.1 输出规范

默认使用简体中文回答，可混用英文技术术语。代码标识符使用英文。

面向用户的结论应：

- 先给核心判断，再给必要依据。
- 明确区分事实、来源声明、推断、假设和待验证问题。
- 对技术方案说明适用场景、不适用场景、优点、缺点和实验验证方向。
- 对架构设计说明涉及层、边界、不解决的问题和交付产物。
- 避免把调研设想写成已定方案。
- 避免堆砌实现细节，除非用户正在讨论实现或实验方案。
- 不使用固定模板或装饰性符号，保持短、清楚、可执行。

文档输出应：

- 使用清晰标题和短段落。
- 保持术语一致。
- 给出可维护的目录结构。
- 对新增规范或抽象说明适用范围。
- 需要长期维护的内容写入 `docs/`，不要只留在对话中。

### 10.2 Commit 规范

用户要求提交时，commit message 使用：

```text
<type>(scope): <summary>
```

`scope` 可选；`summary` 使用中文、动词开头、长度不超过 50 字、不加句号。常用 `type`：`feat`、`fix`、`refactor`、`docs`、`test`、`chore`。
